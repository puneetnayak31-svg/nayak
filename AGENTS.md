# AGENTS.md

Instructions for AI coding agents (Codex, Claude Code, Cursor, Copilot, Gemini, Aider…) working in this repository. Humans: start with `README.md` and `docs/HANDOFF.md`.

## Project in one paragraph

HIPL (Hinduism in Public Life) is a static website generated by a Python standard-library build (`hipl-website/build.py` + `hipl-website/sitekit/`) from HTML templates (`src/pages/`) and JSON content (`src/data/`). It also has a small CMS server (`hipl-website/cms/server.py`) that edits the JSON, receives the public forms, drafts Explorations pages with Claude (`cms/ai.py`) and serves the built site from `dist/`. There is no framework, no database, no npm build. Read `docs/ARCHITECTURE.md` before larger changes.

## Read first: what the owner wants

Before building **any** page, feature, component or content, read:

1. **`docs/BRIEF.md`**: the owner's instructions and the decisions log (D1–D16). These are binding; don't reverse one without the owner's approval. If a request conflicts with one, say so and ask.
2. **`docs/DESIGN-SYSTEM.md`**: how to look and sound like HIPL (Sabha brand: palette, type, logo, layout, components, motion, voice) and the checklist for any new UI. Reuse what's on `/components.html` before inventing anything.
3. **`docs/reference/`**: the owner's original specs (product plan, Explorations & Write for HIPL spec, brand guidelines). Use them for anything the brief doesn't cover.

The short version:
- HIPL is a modern, non-partisan ideas platform about Hindu thought: credible, warm, evidence-led. It is not a religious portal or a political campaign.
- Visually: Midnight and Chalk with a Saffron signature; Marigold and Lotus only as sparks. Unbounded headlines, Instrument Sans text, Mukta for Devanagari. Square corners, flat colour, no shadows or glows. The breathing sabha sun is the signature motion.
- Pages should be immersive and interactive, shareable (`data-share-card`), editable from the CMS (fields in `content_model.py`, not hard-coded text), mobile-first, and still work offline from `file://`.
- Keep 100 Questions simple (no Explorations links). The founders are Prannv Dhawan and Shivom Singh Lovell. Never invent facts.

## Commands (run from `hipl-website/`)

```bash
python3 build.py                 # build dist/ (deterministic)
python3 tools/check.py           # REQUIRED before you finish: compile + all tests (build, links, data, design rules, XSS, CMS API)
python3 tools/check.py --dist    # what CI runs: also fails if committed dist/ is stale
python3 -m unittest tests.test_cms -v          # one suite
python3 cms/server.py --no-browser             # CMS at http://localhost:8800/admin (password printed)
python3 tools/find_placeholders.py --where     # remaining [PLACEHOLDERS] and VERIFY markers
```

Definition of done: `python3 tools/check.py` passes, `dist/` is rebuilt and committed alongside source changes, and the docs are updated if behaviour changed.

## Hard rules

1. **Python 3.9 compatible, standard library only.** The one exception is `anthropic`, imported lazily inside `cms/ai.py`. Do not use `match`, `X | Y` unions or `zip(strict=)`, and do not put backslashes or reused quotes inside f-string expressions. CI runs 3.9.
2. **UTF-8 always.** Pass `open(..., encoding="utf-8")`. Write JSON with `ensure_ascii=False, indent=2` plus a trailing newline. Devanagari must survive.
3. **Escape all content.** Use `esc()` in `build.py` and `ESC()` or `md.inline()`/`md.render()` in `sitekit`. Never put data into HTML unescaped. In JS, set user text with `textContent`, not `innerHTML`. `tests/test_sitekit.py` fails on XSS.
4. **No new dependencies, frameworks or build steps** (npm, bundlers, CSS preprocessors, databases) without the owner's approval.
5. **Never commit secrets or state:** `hipl-website/cms/state/`, `deploy/.env`, API keys.
6. **Keep the build deterministic** (no `datetime.now()` in the output), so the CI freshness check works.
7. **Keep the shared schema the single source of truth.** Add block fields in `sitekit/schema.py` only. The CMS forms and the AI JSON schema derive from it.
8. **Accessibility.** One `<h1>` per page. Real `<button>`s. A text fallback for visual interactives. Alt text for images.
9. **Brand.** Palette tokens only, brand fonts only, square corners, no glows (`tests/test_design.py`). Follow `docs/DESIGN-SYSTEM.md` §10 for any new UI.
10. **Tests.** Add or extend a test in `hipl-website/tests/` for any behaviour you change in `build.py`, `sitekit/` or `cms/`.

## Editorial rules (content is part of the product)

HIPL's credibility depends on these. They apply to any content you write or edit:

- **Never invent** quotations, verses or verse numbers, translations, dates, statistics, people, speakers, venues or "scholars say" claims. If you don't have it from the owner or a cited source, write a `[PLACEHOLDER]` (for example `[SPEAKER NAME]`) or mark it `[VERIFY]`.
- **Name the version:** which text, edition, translation, tradition or region.
- Show more than one interpretation where they exist. Frame modern relevance as a question. No preaching, no politics, no claims that ancient texts "proved" science.
- Put a claim label (`text`, `tradition`, `historians`, `debate`, `asks`) on key passages in Explorations.
- Sample content keeps `"status": "sample"`. Don't promote it to `published`.
- Voice: curious, confident, warm, evidence-led. Plain words. Explain each Sanskrit term on first use. No emoji.
- The full rules are `EDITORIAL_RULES` in `hipl-website/cms/ai.py` and `hipl-website/EDITOR-GUIDE.md`.

## Gotchas

- `dist/` is committed. After changing sources, run `python3 build.py` and commit `dist/` with the change.
- `{{root}}` is a relative path (`""`, `"../"`…). Internal links must use it so pages work from `file://` and from subfolders. Never hard-code `/`-absolute links in templates.
- Team members are keyed by `name` in the CMS, so names must be unique.
- The CMS keeps sessions and AI jobs in memory. Restarting it signs editors out.
- `HIPL_TRUST_PROXY=1` only behind a reverse proxy (otherwise IPs can be spoofed).
- The AI Composer has not been run against the live API yet. If you have a key, test it and report what breaks. Without one, don't claim it works.
- Some sandboxes intercept HTTPS. If `pip` fails with certificate errors inside Docker, that is the environment, not the Dockerfile.

## Git

- Small, focused commits with descriptive messages. Don't rewrite shared history.
- Deploy from `main`. Content commits from the server come from `deploy/sync-content.sh` ("Content update from the CMS …"), so merge them and don't overwrite them.
