# Putting HIPL online

The website in `hipl-website/` is a static site: plain HTML, CSS and JavaScript generated by `build.py`. It needs no server and no database, so it can go live today on any static host. The forms work in the browser now and only need to be connected to a backend before launch.

## 1. Build

```bash
cd hipl-website
python3 build.py            # writes dist/
```

Requirements: Python 3.9+, nothing else. (Regenerating the logo SVGs needs `pip install fonttools brotli`; rendering the launch-kit images needs Node and Playwright.)

Before the real launch, open `build.py` and set `SITE_URL` to the real domain, then rebuild. It is used for canonical links, share images and the sitemap.

## 2. Host (pick one)

**Vercel (recommended, matches the plan).**
1. Push this repository to GitHub (already done on branch `claude/funny-keller-lv40pb`).
2. In Vercel: *Add New → Project → Import* the repo.
3. Root directory: `hipl-website`. Build command: `python3 build.py`. Output directory: `dist`.
4. Add your domain under *Settings → Domains*. `vercel.json` already turns on clean URLs (`/explorations/hindu-universe/dharma` without `.html`).

**Netlify.** Base directory `hipl-website`, build command `python3 build.py`, publish directory `hipl-website/dist`. Turn on "Pretty URLs".

**GitHub Pages.** Build locally and publish `dist/` with a Pages action. Links work with `.html` URLs.

## 3. Connect the forms

Every form has `class="js-form"` and a `data-kind`. Today the script in `assets/js/site.js` validates the form, checks the honeypot field and shows the confirmation message. Look for the comment `Production: POST to /api/forms/<kind>`. Replace that point with a `fetch()` to your endpoint.

| `data-kind` | Where it should go |
|---|---|
| `dispatch` | Newsletter provider API (for example Beehiiv), with double opt-in |
| `question` | 100 Questions moderation inbox (CMS collection or a sheet) |
| `rsvp` | Dialogue RSVP list + confirmation email |
| `dialogue-question` | Moderator's question list |
| `circle` | Reading Circle sign-ups + confirmation email with the guide |
| `pitch` | Voices inbox with statuses Received → … → Published; confirmation email; guardian email for under-18s; file upload ≤ 5 MB (.docx/.pdf) |
| `guest` | Interviews team inbox |
| `correction` | Editors' corrections inbox |

The quickest no-code option is a form service (for example Formspree or Basin) per form. The cleanest is a small serverless function (`/api/forms/[kind]`) that verifies a Cloudflare Turnstile token, stores the entry, and sends a confirmation through Resend.

Keep the consent checkboxes and the hidden `website` honeypot field on every form.

## 4. Analytics (cookieless)

Add Plausible (or Umami) to the `<head>` in `build.py`. `site.js` already sends events through `window.plausible` when it exists: form submissions, filter use, dilemma choices, poll votes, chapters reached, concept pop-ups, share clicks and card-image saves (spec section 8.6).

## 5. Growing into the full plan (Next.js + Payload CMS)

The plan asks for an editor-friendly CMS. This static build is the design system and the content model, ready to move into one:

- **Design system:** `assets/css/site.css` holds every token, component and layout rule. Port the tokens into Tailwind's theme and the components into React one to one.
- **Content model:** `src/data/explorations.json` already matches the CMS types in the Explorations spec (series, entries with number, type, level, read time, topics, priority and the sensitive flag, and concepts). Add Payload collections for Exploration, Concept, Source, Voices Article, Contributor, Voices Pitch, Topic and Media, plus Dialogue, Interview, Question, Reading Circle and Dispatch Issue.
- **Components:** each interactive (Knowledge Cards, Meaning Layers, What Would You Do?, Compare Cards, Map, Timeline, Poll, Claim Label, Concept Pop-up, Character Cards, Pull Quote, Chapter) is a self-contained block in `site.js` driven by data attributes, so each becomes a Payload block with the same fields.
- **Workflow:** statuses Draft → Fact-check → Expert review → Ready → Published, roles Admin, Editor, Fact-checker and Contributor coordinator, and a review-due date per entry.

Until then, editors can update content by editing the files in `src/pages/` and `src/data/` (see `hipl-website/EDITOR-GUIDE.md`) and redeploying. Vercel rebuilds automatically on every push.
